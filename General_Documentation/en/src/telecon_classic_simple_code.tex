\begin{abstract}
This note is the Arduino sketch in the folder
\texttt{Classic\_Simple/TeleCon\_Classic\_Simple/}.
The phone setting is Classic + Simple. The board name is
\str{ESP32-TC-RC-BT-Simple}. The handshake is
\str{RC:CONNECT,proto,simple}.
The declarations of each file come first: includes, macros,
variables, and types. Then each function, with its code in the IDE
colors.
The two complete files are the annexes.
\end{abstract}

\section{File declarations}
\label{sec:decl}

This is the head of each file: what the compiler sees before the first
function body. The code uses the IDE colors. The line numbers are the
line numbers of the file.

\subsection{In \texttt{TelemetryChannels.h}}

The \texttt{.ino} includes this header, so these names exist before
\nm{kTelemetryChannels[]}.

\hsnippet{1}{15}

\kw{\#pragma once} brings the file into the build once, even if
something includes it twice. \texttt{Arduino.h} brings
\typ{uint8\_t}, \fnm{analogRead}, \fnm{digitalRead}, and
\fnm{ledcRead}. The comment in the middle generates no code: CH1
is \str{v0}, CH8 is \str{v7}, and each sample is a byte 0--255.

\hsnippet{17}{33}

\nm{TelKind} says where a row's byte comes from.
\nm{TEL\_VEHICLE} calls \fnm{telemetryVehicle()}.
\nm{TEL\_ADC} reads an analog pin. \nm{TEL\_GPIO} reads a digital
pin. \nm{TEL\_PWM} reads an LEDC duty. The numeric value starts at
0 and continues in order.

\nm{TelVehicle} names the built-in signal, only when the row is
\nm{TEL\_VEHICLE}. \nm{TEL\_TEMP} is temperature,
\nm{TEL\_THROTTLE} is the throttle, \nm{TEL\_BATT} is the battery,
\nm{TEL\_STEER} is steering, \nm{TEL\_LIGHTS} is the lights,
\nm{TEL\_KNOB\_L} and \nm{TEL\_KNOB\_R} are the knobs, and
\nm{TEL\_RY} is the right stick's Y axis. The factory table does
not use \nm{TEL\_RY}.

\hsnippet{35}{44}

\nm{TelChannel} is one row of the table. \nm{kind} is the
\nm{TelKind}. \nm{vehicle} is the \nm{TelVehicle}; an ADC, GPIO,
or PWM row does not read that field. \nm{pin} is the GPIO, or
$-1$ when the row has no pin. \nm{ledcChannel} is the LEDC channel
on core 2.x, or $-1$ when there is no PWM. \nm{dutyMin} and
\nm{dutyMax} are the ends of the duty range: the minimum is sent
as 0 and the maximum as 255.

\nm{TelVehicleFn} is the type of the pointer to
\fnm{telemetryVehicle()}: it takes a \nm{TelVehicle} and returns
a byte.

\subsection{In \texttt{TeleCon\_Classic\_Simple.ino}}

\inosnippet{1}{14}

The comment block does not enter the binary. It states the Bluetooth
name, the PIN, and the handshake line. \texttt{BluetoothSerial.h} is
the Classic port. \texttt{TelemetryChannels.h} is the header above.

\inosnippet{16}{45}

\nm{BT\_NAME} is the name Android sees when pairing.
\nm{BT\_PIN} is \str{1234}. \nm{APP\_PREFIX} has to be
\str{RC} and \nm{PROTO\_WIRE} has to be \str{simple}: those are
the two strings \fnm{handleConnect()} accepts.
\nm{SERIAL\_BAUD} is 115200 for the monitor.

\nm{ENABLE\_DEBUG} at 1 writes to the monitor.
\nm{DBG\_PRINT} becomes \ser{print}.
\nm{DBG\_PRINTLN} becomes \ser{println}.
\nm{DBG\_PRINTF} becomes \ser{printf}.
At 0 those three macros become empty and the link stays the same.

\nm{TELEMETRY\_DATA\_MS} is the dashboard period, 500\,ms.
\nm{ENABLE\_PLOT} at 1 sends \str{RC:PLOT}.
\nm{PLOT\_MS} is 50\,ms.
\nm{ENABLE\_SERIAL\_INJECT} at 1 lets you paste a line into the
monitor after the handshake.
\nm{SERIAL\_MAX\_LINE} cuts that line at 192 characters.

\nm{DEMO\_MOTOR\_TEMP} is 90 and \nm{DEMO\_BATT\_PCT} is 76.
They are fixed dashboard numbers until a sensor is fitted.
They do not come from a pin.

\inosnippet{47}{70}

\nm{SerialBT} is the Classic port. \nm{handshakeOk} is the gate:
while it is false there is no \fnm{onControl()}, no \str{RC:DATA},
and no \str{RC:PLOT}. \nm{btWasConnected} stores the client from
the previous pass, so a connect or a drop is noticed once.

\nm{g\_lx}, \nm{g\_ly}, \nm{g\_rx}, and \nm{g\_ry} are the
sticks, from $-100$ to 100. They start at 0. \nm{g\_ly} is the
throttle and \nm{g\_rx} is steering. \nm{g\_lk} and
\nm{g\_rk} are the knobs, from 0 to 1023, and they start at 512.
\nm{g\_sw} is the switch byte. Bit 0 is the lights.

\nm{lastDataMs} marks the dashboard.
\nm{lastPlotMs} marks the plot.
Both store \fnm{millis()}.
\nm{serialLineBuf} gathers the line pasted into the monitor.
It exists only when injection is compiled in.
The \nm{lastPrint*} values store the last printed image of each
axis, knob, and switch. They start at \typ{0xFFFF} or \typ{0xFF}
so the first sample is always printed. They are not sent to the phone.

\inosnippet{72}{84}

These lines are the compiler's notice that each body comes further
down, so \fnm{setup()} and \fnm{loop()} can call them.
\fnm{serialInjectPoll} and \fnm{handleSerialInjectLine} are
declared only when \nm{ENABLE\_SERIAL\_INJECT} is 1. Each body is
in the next section.

\inosnippet{87}{98}

\nm{ENABLE\_STEER\_SERVO} at 1 arms the servo.
At 0 the two servo functions stay empty.
\nm{PIN\_STEER\_SERVO} is GPIO 13.
\nm{CH\_STEER\_SERVO} is LEDC channel 2, the one core 2.x uses.
The \kw{\#ifndef} lets the IDE change the value before this file,
and uses the factory value when nobody changed it.

\inosnippet{100}{114}

\nm{kTelemetryChannels} has eight rows and does not accept a ninth.
Each brace is a \nm{TelChannel}: kind, signal, pin, LEDC channel,
\nm{dutyMin}, and \nm{dutyMax}. Row 0 is CH1 (\str{v0}) and
row 7 is CH8 (\str{v7}).

From the factory, rows 0 to 6 are \nm{TEL\_VEHICLE}: temperature,
throttle, battery, steering, lights, left knob, and right knob.
The pin and the channel are $-1$ because the signal does not come
from a GPIO. Row 7 is the servo's \nm{TEL\_PWM}: pin
\nm{PIN\_STEER\_SERVO}, channel \nm{CH\_STEER\_SERVO}, duty from
204 to 409 (the 1000--2000\,\textmu s travel).

\inosnippet{139}{140}

These two constants sit just before \fnm{steerDutyFromUs()}.
They are outside the header.
\nm{kSteerCenterUs} is 1500\,\textmu s, the center.
\nm{kSteerTravelUs} is 500\,\textmu s to each side of the stick.
\nm{rx} = 0 stays at 1500\,\textmu s.

\section{What each function does}
\label{sec:funcs}

The order follows each file, after the declarations. Under each
signature is the whole function, in the IDE colors. The text uses the
same coloring: orange is a function, from the sketch or from a library
(\fnm{onControl()}, \fnm{print}, \fnm{ledcWrite}), and purple is a
name from this project (\nm{BT\_NAME}, \nm{g\_lx},
\nm{TEL\_TEMP}).

\nm{DBG\_PRINT}, \nm{DBG\_PRINTLN}, and \nm{DBG\_PRINTF} are
macros. With \nm{ENABLE\_DEBUG} at 1 they write to the serial
monitor. At 0 the compiler removes them.

\subsection{In \texttt{TeleCon\_Classic\_Simple.ino}}

\begin{fnblock}
\fn{\typ{uint8\_t} \fnm{telemetryVehicle}(\nm{TelVehicle} \nm{id})}{116}{137}
Line 116. Returns the byte 0--255 of a built-in signal, the one a
\nm{TEL\_VEHICLE} row asks for. \nm{TEL\_TEMP} is the constant
\nm{DEMO\_MOTOR\_TEMP}. \nm{TEL\_THROTTLE} is the magnitude of
\nm{g\_ly}. \nm{TEL\_BATT} scales \nm{DEMO\_BATT\_PCT} from
0--100 to 0--255. \nm{TEL\_STEER} is the magnitude of \nm{g\_rx}.
\nm{TEL\_LIGHTS} is 255 when bit 0 of \nm{g\_sw} is set, and 0
when it is clear. \nm{TEL\_KNOB\_L} and \nm{TEL\_KNOB\_R} map
the knob from 0--1023 to 0--255. \nm{TEL\_RY} is the magnitude of
\nm{g\_ry}. Any other \nm{id} returns 0. Throttle, steering, and
\nm{TEL\_RY} drop the sign: both ends of the stick produce the
same byte.

\end{fnblock}

\begin{fnblock}
\fnstep{142}{145}{\typ{uint32\_t} \fnm{steerDutyFromUs}(\typ{int} \nm{us})}{%
Line 142. Turns a pulse width, in microseconds, into a 12-bit LEDC
duty: pulse $\times 4095 / 20000$. It first limits the pulse to
500--2500\,\textmu s. 1500\,\textmu s lands at the center of a 20\,ms
frame.}

\end{fnblock}

\begin{fnblock}
\fnstep{147}{151}{\typ{uint32\_t} \fnm{steerDutyFromRx}(\typ{int} \nm{rx})}{%
Line 147. Limits \nm{rx} to $-100\ldots 100$, turns it into
microseconds (0 is 1500\,\textmu s, full travel is $\pm 500$\,\textmu s),
and calls \fnm{steerDutyFromUs}. The phone trim is already inside
\nm{rx}.}

\end{fnblock}

\begin{fnblock}
\fntwo{\typ{void} \fnm{steerServoBegin}()}{153}{163}{174}{174}
Line 154, or line 174 when \nm{ENABLE\_STEER\_SERVO} is 0.
With the servo on, it sets a 50\,Hz, 12-bit PWM on
\nm{PIN\_STEER\_SERVO} and writes the center. On core 3.x the
channel is attached by pin number (\fnm{ledcAttach},
\fnm{ledcWrite}). On 2.x it uses \nm{CH\_STEER\_SERVO}
(\fnm{ledcSetup}, \fnm{ledcAttachPin}, \fnm{ledcWrite}).
With the switch at 0 the function does nothing.

\end{fnblock}

\begin{fnblock}
\fntwo{\typ{void} \fnm{steerServoWriteRx}(\typ{int} \nm{rx})}{165}{172}{175}{175}
Line 165, or line 175 when the servo is off. It computes the duty
for \nm{rx} and writes it. The empty version only discards
\nm{rx}, so the compiler stays quiet about an unused parameter.
\fnm{applyFailSafe()} calls it with 0, which is the center.

\end{fnblock}

\begin{fnblock}
\fn{\typ{void} \fnm{onControl}(\typ{int} \nm{lx}, \typ{int} \nm{ly}, \typ{int} \nm{rx}, \typ{int} \nm{ry}, \typ{int} \nm{lk}, \typ{int} \nm{rk}, \typ{uint8\_t} \nm{sw})}{178}{187}
Line 178. Runs once for each \str{RC:CTRL} line. It prints the
change on the monitor, moves the servo with \nm{rx}, and leaves the
\cmt{YOUR CODE HERE} block for whatever should follow the stick: motor
PWM, a pan servo from \nm{rk}, a lights pin from
\nm{sw} \& 0x01. The \texttt{(}\typ{void}\texttt{)} casts silence the
warning for values the starter sketch does not use yet. Remove the
cast of a value when you start using it.

\end{fnblock}

\begin{fnblock}
\fn{\typ{void} \fnm{onButton}(\typ{int} \nm{id})}{189}{198}
Line 189. Runs once for each \str{RC:BTN}. It prints the id. The
factory comment leaves id 2 for a short horn pulse and id 4 for
centering a pan servo. Those two bodies are empty. A button that must
stay down belongs as a bit of \nm{sw} inside \fnm{onControl()},
because \str{RC:BTN} is the press, and the held level travels in
\str{RC:CTRL}.

\end{fnblock}

\begin{fnblock}
\fn{\typ{void} \fnm{setup}()}{200}{242}
Line 200. Starts serial at 115200, waits 200\,ms, centers the servo,
turns Secure Simple Pairing off, sets the PIN \str{1234}, and opens
Bluetooth Classic with \nm{BT\_NAME}, as a slave and without BLE. If
\nm{SerialBT}\texttt{.}\fnm{begin} fails, it prints the failure and
stays in \kw{while} (\typ{true}). The banner after that is debug only:
the name, the handshake, and sample lines for the monitor.

\end{fnblock}

\begin{fnblock}
\fn{\typ{void} \fnm{loop}()}{244}{302}
Line 244. Arduino calls \fnm{loop()} again and again, from the moment
\fnm{setup()} finishes. Each pass follows these steps, and the next
one starts when the previous one has finished.

\fnstep{245}{256}{1. Bluetooth client}{%
  Reads \nm{SerialBT}\texttt{.}\fnm{hasClient()} and compares it with
  \nm{btWasConnected}. If it changed, it stores the new state.
  If the phone just arrived, it calls \fnm{resetHandshake()}:
  \nm{handshakeOk} stays false, and the monitor says it is waiting
  for \str{RC:CONNECT,proto,simple}.
  If the phone just left, it calls \fnm{applyFailSafe()}
  (sticks at 0, knobs at 512, switches at 0, servo at center) and
  then \fnm{resetHandshake()}.
  If the client is unchanged, this block calls nobody.}
\fnstep{258}{264}{2. Bluetooth lines}{%
  While \nm{SerialBT} has bytes, it reads up to
  \str{\textbackslash n}, strips spaces with \fnm{trim()}, and, if
  text remains, calls \fnm{handleLine()}.
  A valid \str{RC:CONNECT,proto,simple} line in this same pass sets
  \nm{handshakeOk} true before the timers below.}
\fnstep{266}{268}{3. Serial monitor}{%
  With \nm{ENABLE\_SERIAL\_INJECT} at 1, it calls
  \fnm{serialInjectPoll()}.
  A monitor line that starts with \str{RC:DATA} or with
  \str{RC:PLOT} goes out to the phone at that moment.
  With the switch at 0, this block is left out of the binary.}
\fnstep{270}{270}{4. Handshake gate}{%
  If \nm{handshakeOk} is false, \fnm{loop()} ends at that
  \kw{return}.
  The dashboard and the plot wait for the answer from
  \fnm{handleConnect()}: \str{RC:ACK,app,RC}.}
\fnstep{272}{272}{5. Clock}{%
  Stores \fnm{millis()} in \nm{now}.
  The dashboard and the plot use this same instant, each with its
  own mark. Meeting one deadline does not restart the other.
  Both can come due on the same pass: the dashboard first, then
  the plot.}
\fnstep{274}{286}{6. Dashboard, every \nm{TELEMETRY\_DATA\_MS} (500\,ms)}{%
  When \nm{now} $-$ \nm{lastDataMs} reaches the period, it stores
  \nm{now} in \nm{lastDataMs} and builds an \str{RC:DATA} line.
  \str{left} is \fnm{abs}(\nm{g\_ly}) * 25 / 10: throttle 100
  goes out as 250, and the phone reads it as speed $\times 10$.
  \fnm{abs()} sends the magnitude, so full reverse throttle also
  goes out as 250.
  \str{right} stays fixed at 0.
  \str{lo,1,ro,0,lg,1,rg,0} are the panel lamps, also fixed.
  \str{analog} copies \nm{DEMO\_MOTOR\_TEMP} (90) and \str{batt}
  copies \nm{DEMO\_BATT\_PCT} (76).
  \str{led} is \nm{g\_sw} in two hexadecimal digits.
  \fnm{sendLine()} sends that line.}
\fnstep{288}{301}{7. Plot, every \nm{PLOT\_MS} (50\,ms)}{%
  This block enters the binary when \nm{ENABLE\_PLOT} is 1.
  When \nm{now} $-$ \nm{lastPlotMs} reaches the period, it stores
  \nm{now} in \nm{lastPlotMs}, calls \fnm{telemetryReadAll()} with
  \nm{kTelemetryChannels} and \fnm{telemetryVehicle}, and sends
  \str{RC:PLOT} from \str{v0} to \str{v7}, in the order of the eight
  rows.
  With \nm{ENABLE\_PLOT} at 0, this block is left out of the binary.}

\end{fnblock}

\fn{\typ{String} \fnm{getValue}(\typ{const} \typ{String}\& \nm{line}, \typ{const} \typ{char}* \nm{key})}{425}{447}

\begin{fnblock}
\fn{\typ{void} \fnm{handleConnect}(\typ{const} \typ{String}\& \nm{app}, \typ{const} \typ{String}\& \nm{line})}{449}{475}
Line 449. Requires two things, ignoring case. The name before the
colon has to be \nm{APP\_PREFIX} (\str{RC}). The \str{proto}
value has to be \nm{PROTO\_WIRE} (\str{simple}). If the name does

\begin{fnblock}
\fn{\typ{void} \fnm{handleLine}(\typ{const} \typ{String}\& \nm{line})}{477}{508}
Line 477. If the line has no colon, it returns. It splits the app
and the type (the text up to the first comma). \str{CONNECT} calls
\fnm{handleConnect} even when the handshake is not ready yet. Any
other type is ignored while \nm{handshakeOk} is false, and also
when the app is not \str{RC}. \str{CTRL} stores \nm{lx},
\nm{ly}, \nm{rx}, \nm{ry}, \nm{lk}, \nm{rk}, and
\nm{sw} (the \nm{sw} field is read in hexadecimal) and calls
\fnm{onControl}. \str{BTN} calls \fnm{onButton} with the

from the phone does nothing: this sketch sends those lines, and it
does not obey them.

\end{fnblock}

\subsection{In \texttt{TelemetryChannels.h}}

The file declares the types the three functions use.
\nm{TelKind} is the source of the row: vehicle, ADC, GPIO, or PWM.
\nm{TelVehicle} is the built-in signal (\nm{TEL\_TEMP},
\nm{TEL\_THROTTLE}, \nm{TEL\_BATT}, \nm{TEL\_STEER},
\nm{TEL\_LIGHTS}, \nm{TEL\_KNOB\_L}, \nm{TEL\_KNOB\_R},
\nm{TEL\_RY}). \nm{TelChannel} stores the kind, the signal, the
pin, the LEDC channel, and the duty range. \nm{TelVehicleFn} is
the pointer to \fnm{telemetryVehicle()}.

\begin{fnblock}
\fnh{\typ{uint8\_t} \fnm{telemetryReadPwm}(\typ{const} \nm{TelChannel}\& \nm{ch})}{46}{56}
Line 46. If \nm{dutyMax} is not greater than \nm{dutyMin},
it returns 0. It reads the duty that is already running: on core 3.x
with \fnm{ledcRead} of the pin number, on 2.x with \fnm{ledcRead}
of the channel number. It clips that duty to
\nm{dutyMin}\ldots\nm{dutyMax} and scales it to 0--255. The
factory servo row uses 204\ldots409, which is the
1000--2000\,\textmu s travel; the center comes out near 128. The pin
has to be attached in \fnm{setup} before this function reads it.

\end{fnblock}

\begin{fnblock}
\fnh{\typ{uint8\_t} \fnm{telemetryReadOne}(\typ{const} \nm{TelChannel}\& \nm{ch}, \nm{TelVehicleFn} \nm{vehicle})}{58}{71}
Line 58. One byte, according to \nm{ch}\texttt{.}\nm{kind}.
\nm{TEL\_ADC} reads the pin and scales 0--4095 to 0--255; a negative
pin returns 0. \nm{TEL\_GPIO} returns 255 or 0 from
\fnm{digitalRead}; an output pin reports the level that was written.
\nm{TEL\_PWM} calls \fnm{telemetryReadPwm}. Any other kind calls
\fnm{vehicle}(\nm{ch}\texttt{.}\nm{vehicle}). If that pointer is
null, it returns 0.

\end{fnblock}
